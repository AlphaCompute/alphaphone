## How to interpret suite results

There are **43 argument-gated test methods in 36 native test classes**, counted from current source: 110 total `@Test` methods in 64 classes, leaving 67 methods without argument gates. These are source counts, not the Build72 archived suite’s 101 reported methods/35 assumptions. The new combined-agent restart, Photos batch and Browser share methods, plus notification-channel and workflow lifecycle methods are counted even where runtime acceptance is pending. This includes the Inbox `processPhase` method gated by its `@Before` fixture setup (the setup method itself is not a test), and one phased method counted once regardless of phase count. `Assume` imports in `FlowInstrumentedTest` are unused, not another gate. No `@Ignore` cases were found. A full-suite `OK` count or a listed class is insufficient: absent arguments cause the methods below to exit without their integration assertions. Report executed gated flows separately.

Use a disposable Pixel-class emulator. Every row requires an app APK and matching test APK from the same source/build, tested independently for standalone and launcher. Only `android-smoke.mjs` explicitly manages/restores HOME. Installing the launcher APK in another runner does not prove HOME-role behavior. Most older wrappers verify the app hash against `artifacts/apk-manifest.json` but load test APKs from `android/app/build/outputs/...`; archive/hash and verify that test APK too. The document/reminder phased runners accept explicit app/test APK paths and record both hashes.

Set `ANDROID_SERIAL=emulator-N` explicitly. For direct instrumentation, install the matching pair first, then use:

```sh
adb -s "$ANDROID_SERIAL" shell am instrument -w -r -e class ai.elizaresearch.alphaphone.CLASS -e ARG VALUE ai.elizaresearch.alphaphone.test/androidx.test.runner.AndroidJUnitRunner
```

Class selectors can include `#method`; replace the literal placeholders using the table. Keep all tokens and pairing material in the owner-only files managed by the runners, never in command arguments or logs. Do not run tests concurrently against one emulator or restart the shared agent under another run.

### Newly identified execution blockers

- **Legacy live-agent tests versus chooser:** the DevelopmentAgent fallback transport exists only in `ELIZA_DEV_ALLOW_TEST_MOCKS=1` debug builds. Even there, `agent-adapter.ts` deliberately refuses DevelopmentAgent fallback whenever `alpha.connection.selection.v1` exists. `AppNavigation.request` closes an initial connection chooser by explicitly choosing offline, which persists such a selection. The connected runner only installs a legacy token; it does not establish a current supported selected connection. Therefore running its three legacy model tests on an offline-selected/current fresh chooser session does not establish the intended transport. Migrate these assertions to an explicitly selected supported local connection, or define a reviewed explicit development fixture mode; do not remove the offline boundary or erase selection to conceal this incompatibility.
- **Workflow fixture identity (runner repaired):** `ALPHA_WORKFLOW_FIXTURE_ID` now explicitly connects a reviewed dynamic arithmetic fixture to native execution; no default is retained. The runner checks exact canonical source and authenticated list/detail identity/version/status before obtaining pairing material. Build69 context and Build71 cancellation/approval use explicitly reviewed fixtures; Build72 submission recovery passes both after the earlier standalone pairing fixture failure. Source version can change after setup; runtime review/version checks remain necessary, and this test assumes no concurrent editor for the disposable fixture.
- **Artifact pairing:** app hash validation alone cannot prove test/source correspondence; freeze and archive all four APKs plus source fingerprints before matrix runs.
- **Instrumentation changes the target process:** default `am instrument` force-stops its target. Use the documented external witness for reboot alarms, and staged process tests for persistence. Do not insert another instrumentation launch between reboot and the receipt/notification observation.
