## Exact prototype contract and current gaps

The reference-owned model at `apps/app/src/prototype/model.js:4329` defines these seven step chips. Its objects and prose are visual reference data, not executable permissions. `WF_TRIG` at4341 defines five trigger chips. Builder handlers at4687 onwards already describe ordered diagram editing, per-step sheet, presets, arbitrary text, up/down, delete, trigger chips, Save/Cancel and Describe. Current production `workflow-adapter.ts` replaces New with the unavailable handler and provides only metadata Change; it does not implement this authoring contract.

Input fields must match their declared type, not an unrestricted sentence that is later evaluated as code. Cancel discards only the draft; deleting a step does not mutate a running definition.

## Why the current source API is insufficient

Reviewed `plugin-workflow/src/routes/workflow-routes.ts:171` exposes POST `/workflows/generate`; it calls `generateWorkflowDraft` in `workflow-service.ts:206`, using TEXT_LARGE JSON output parsed into a source-bearing definition. POST `/workflows` delegates `deployWorkflow` at232, which may update a supplied existing ID and may activate. These are not safe phone creation/idempotency APIs.

`smithers-runtime.ts:195` validates only source/import/default-export/legacy-package patterns; at287 the module is imported. An Approval node inside that module does not constrain top-level import effects. No “preview” may import untrusted source. Existing hand-authored arithmetic/approval fixtures prove the reviewed runtime, not safety of arbitrary generated workflows.

Current `/status` advertises manualSubmissionProtocol, approvalReceiptProtocol, metadataMutationProtocol and lifecycleMutationProtocol1; none advertises typed authoring or reliable schedule admission. `connection-ui.tsx:getWorkflowClient` explicitly excludes Cloud. The remote owner route surface must not simply be assumed to work under a Cloud account token.

## Specification and backend authority

Add `phoneWorkflowSpecVersion:1` and a live owner/device/account-scoped catalog, with exact input/output schemas, operation version, effect classification, grant requirements, implementation availability and reason when unavailable. Catalog generation is read-only. A draft has a name, description, trigger, ordered bounded steps, explicit data references and bindings. Suggested limits:32 steps,64KiB spec, bounded text/attachments/read limits, no arbitrary JS/SQL/URL-fetch/code expressions, no credentials or unrestricted plugin names. Every step owns a stable UUID; moving it changes ordering, not identity. References may address earlier typed outputs only; reject forward/cyclic or incompatible references.

Suggested trigger shape uses an explicit union: manual, civil-time, calendar-event, channel-message, geofence, mailbox-event. Implementations are advertised individually. Save rejects unsupported or unresolved entries rather than storing an apparently runnable skeleton. Account and device selection uses server-authorized opaque IDs plus human review labels; labels never authorize access. Record catalog revision, spec digest and fixed executor/template revision in review and execution receipts.

A trusted fixed executor/template is code shipped and reviewed with the server. The user/model supplies validated data only. Avoid routing typed Save into the legacy arbitrary-source deploy method. A fixed Smithers template may be emitted from a closed compiler, but its imports and capability calls must be server-owned and payloads encoded strictly as data. Existing worker isolation does not supply a workflow capability RPC by itself: implement a run/step/spec/version-bound dispatcher before claiming device/connector effects work. No ambient owner bearer, broad runtime plugin invocation or naked client “trusted” flag may cross that bridge.

Use the existing canonical stores rather than introducing another approval queue. For server connector effects, use the canonical Smithers Approval receipt. For phone effects, use the existing durable device approval/claim/journal/receipt authority; the workflow step waits for that exact operation receipt. Do not create a second independent workflow approval for the same phone effect or auto-approve a device proposal from a generic workflow click. The Workflows receipt UI can render the bound device proposal with the same explicit review, but approval remains on the canonical device route.

The current device service requires a trusted turn device context (`plugin-assistant/src/services/device-actions/service.ts`); a scheduled workflow is not such a chat turn. Add an explicit server-side `proposeForWorkflow` entry bound to owner, agent, installation/enrollment, execution, step, spec digest and occurrence. Reuse the existing queue's unique request identity and operation validators. Add no fake conversation or inferred prose command. The phone validates the bound workflow review context and exact step version, then uses its existing native journal before effects. Offline/revoked devices leave a visible waiting/unavailable step and never falsely finish the workflow. Native permissions are rechecked when executing.

## Durable authoring flow

1. New opens the existing builder with an inactive local draft and real capability catalog. Describe sends only the user's explicit draft request and selected bindings; the agent returns the same strict data spec. Unknown fields or invented account IDs are rejected and shown as unresolved.
2. Trigger sheet and step sheets edit typed fields. Reorder/delete update references or explain invalid dependents. Back/Cancel prompts only for unsaved draft loss. Persist user-entered draft privately if needed; do not put draft content into generic agent context.
3. Preview performs structural validation and resolves permission/account/device availability without importing source, invoking models for effect execution, scheduling or writing data. Show exact read scopes, model disclosure, destinations, confirmation requirements, zone and timing policies.
4. Save calls a new owner-scoped creation endpoint with creationUUID + exact spec/catalog/executor digest. One transaction creates a fresh workflow UUID, inactive reviewed spec/version, revision and immutable creation receipt. Same creation key/payload returns the receipt; changed payload conflicts. No supplied existing workflow ID or active=true. Persist only identity/digest for ambiguous submission; reconcile by GET after recreation/restart. Do not retry POST automatically.
5. Change opens the same full builder for typed definitions. Save uses expectedVersion + mutationUUID + exact spec; admission/version updates share the existing definition lock. Source-based legacy workflows keep metadata-only Change and honest editor availability. Edits pause schedules and invalidate previous enable review; they do not silently alter in-flight runs pinned to earlier versions.
6. Test uses the existing reviewed manual submission route; show actual side effects and require explicit approval where specified. Pure preview and Test are distinct. Unknown outcomes retain existing submission locks and canonical reconciliation.
7. Enable is a new atomic owner/expectedVersion/spec-digest/grant-revision mutation with an immutable receipt, not current GET-then-activate. It rechecks capability/revocation and stores trigger intent in the same transaction. A separate idempotent trigger reconciler publishes transport work. Disable blocks new admissions durably first; it does not imply cancellation of running effects. Keep the existing explicit Cancel execution flow.
8. Run history keeps per-step input source identities/revisions, decision/result receipts, skips, permission errors and unavailable-device state. Removal/restore already preserves history; restoration remains paused and requires new enable review.

## Scheduling defaults to implement and display

- **Zone:** pin the IANA zone chosen at creation. Show it in trigger review. Travel/device-zone changes do not silently reinterpret an enabled workflow; explicit zone edit creates a new version and pauses it.
- **Civil time:** implement prototype Every day/Weekdays/Weekends/Mondays/Fridays as calendar-day rules, not24-hour durations. Default gap policy: skip nonexistent local occurrence and record `skipped_dst_gap`. Default fold: earlier occurrence only. Show both policies in timing review. Offset/event triggers use provider event occurrence identity, not just title.
- **Occurrence identity:** immutable triggerID + reviewed trigger revision + local date/time + zone + resolved offset (or exact provider event ID/revision). Enforce a unique durable occurrence row and queued run admission in the same definition-lock transaction. Duplicate dispatch reads the existing receipt.
- **Missed run:** default no catch-up after service/phone downtime. Record bounded missed occurrences and resume at the next future occurrence. An explicit future catch-up mode may allow one latest occurrence within a displayed grace interval; never replay a backlog of communications on startup.
- **Overlap:** default skip new occurrence while a prior run of that workflow is nonterminal, including waiting for approval/device. Persist an explicit skipped-overlap receipt. No unbounded queues or hidden parallel sends. Optional queue/parallel policy must be separately reviewed and tested.
- **Offline/native delivery:** remote trigger firing does not mean the phone effect happened. Keep the step waiting until receipt/deadline; expiry records a non-success outcome. Reconnection must not infer permission or auto-replay an expired proposal.
- **Disable/edit/remove races:** atomic admission rechecks active/version/tombstone/grants. A trigger already claimed but not admitted loses authority after the mutation. Already-admitted runs retain pinned inputs and require explicit cancellation. Startup reconciles desired trigger state; stale transport tasks cannot bypass admission.

`embedded-workflow-service.ts:803` currently computes a next cron time and creates a task keyed only to workflow identity. Its added row lock protects admission/removal races, but there is no full reviewed occurrence, overlap, missed-run or versioned-enable contract. Do not label the above policies implemented yet.

## Responsibility and practical implementation order

**Phone renderer/native:** exact prototype editing/review; native account/device/file selection; permissions; local data read snapshots with explicit consent; approved native effects; durable journal; receipt/playback UI. It does not become a background cloud scheduler or expose arbitrary app data to the model.

**Remote/local agent:** catalog, validated typed specification, deterministic executor, durable creation/edit/enable/occurrence records, canonical decisions, connector/model calls and receipts. Local and remote use the same protocol; remote URLs retain current TLS/auth requirements. Model output is data and never authorization.

**Eliza Cloud:** normal account login/agent selection and runtime routing; OAuth account bindings and provider events where authorized. Add the same typed workflow capability behind actual Cloud runtime routes only after owner principal propagation is verified. Cloud absence is explicit; do not silently run a different local account or request a broad new organization key.

Minimum useful end-to-end delivery is **New → manual/time trigger → explicitly scoped Read selected note/calendar range → If bounded predicate → Write summary/draft → approved save-to-Notes → optional app notification → explicit Listen → Save inactive/Test/Enable/history**. This is materially more than metadata or a synthetic arithmetic authoring demo. It requires the typed native read/proposal bridge, Notify operation and durable civil trigger lifecycle described above. Split engineering delivery into independently tested patches, but keep the unfinished Send/Event/Message/Place/Email/Do variants visible in the acceptance ledger; completion of this path is not full-builder acceptance.

Next patches in dependency order: (1) strict catalog/spec + deterministic no-effect validation + durable create/edit receipts; (2) workflow-bound native read and approved operation dispatch with real Notes/Calendar snapshots; (3) exact-version enable and durable civil occurrences; (4) actual prototype builder and explicit Test/history; (5) Gmail Send/event sources and remaining Do capabilities with their own account/grant proofs. No generated-source workaround is needed for any phase.
