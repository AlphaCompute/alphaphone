# Browser continuity and durable bookmarks

Build54 verified on the Pixel-class emulator: both standalone and launcher passed the actual HTTPS two-tab/app-switch/history/Activity-recreation flow and the separate-process bookmark save/restore/remove/restart flow. Exact app/test APK hashes, terminal logs, phase results and scoped cleanup are archived in `test-results/prototype-build54/browser-continuity/` and `bookmark-restart-{standalone,launcher}/`. This does not establish cloud sync or a durable cookie/profile policy.

A normal Browser → another app → Browser transition previously reset the renderer's tab identities while the corresponding isolated native WebViews remained alive. The production browser now retains tabs, selected tab, in-memory history and bookmark state across view resets. These keys are only renderer memory; they are not a disk session restore. Overlays still reset and native surfaces still hide on departure.

Explicit user bookmarks use the existing menu/library without new chrome. Native Android stores at most 100 unique HTTPS URLs (4096 characters each) encrypted with AES-GCM and an Android Keystore key. Embedded credentials, whitespace/control characters and non-HTTPS schemes are rejected. Bookmark changes are serialized and the renderer changes only after native commit succeeds. Failed decryption or writes preserve the existing ciphertext and report failure instead of silently replacing it. The store contains no page content, form data, history, cookies or credentials. URLs are not sent to the agent. The native child website has no app bridge. Bookmark URLs can themselves contain private query parameters, which is why plaintext preferences are not used.

Cold startup restores only explicit bookmarks. It opens one empty tab; no saved website or history is loaded automatically. Tab profiles retain their existing ephemeral isolation lifecycle. There is no account synchronization, vault credential storage or automatic page summarization.

`BrowserContinuityInstrumentedTest#tabsSurviveAppNavigationAndBookmarksSurviveActivityRecreation` exercises two actual HTTPS WebViews with independent storage, native back/forward, app switching, user bookmark creation/navigation/removal, native ciphertext readback and Activity recreation. This test is not process-death evidence.

`node scripts/test-bookmark-restart.mjs APP.apk MATCHING_TEST.apk OUTPUT` with `ANDROID_SERIAL=emulator-N` runs `bookmarkProcessRestartPhase` in separate instrumentation processes. It saves a UUID-scoped bookmark through the real UI, force-stops the app, requires a different PID, verifies no automatic native page and a restored library entry, explicitly opens that bookmark, removes it through the UI, then force-stops again and verifies removal in another PID. Cleanup removes only its recorded synthetic URL; all other bookmarks are preserved. APK hashes and phase outcomes are archived. Both distribution variants passed all four phases: prepare, verify in a new PID, verifyRemoved in another PID, and scoped cleanup.

## Android provider capability requirement — September 30

Build58 added profile-scoped browsing-data purging and rejects native browser creation if `WebViewFeature.DELETE_BROWSING_DATA` is unavailable. The original Pixel emulator used AOSP WebView 124.0.6367.219, whose exact Chromium feature list omits `WEB_STORAGE_DELETE_BROWSING_DATA`; this caused both continuity tests to fail before any document loaded. Versions 133 and 138 inspected in official Chromium source advertise the capability. Feature detection, rather than an assumed OS/API version, is the runtime contract. Production distribution still requires a maintained, trusted WebView provider and its update policy.

For development verification only, the emulator was updated to AOSP WebView 138.0.7204.67, pinned official ARM64 payload. Its upstream certificate did not match the emulator's public AOSP test signer, so a clearly labeled local derivative was signed with that same public test key. All 619 non-signing payload entries, including compressed bytes, matched upstream. This is not an upstream-signed package or a production distribution candidate. Exact source pins, certificate comparisons, payload manifest and installed-provider readback are in `test-results/webview-provider-research/`. The existing system partition was not removed or remounted. Native behavior must still pass on the updated provider.
