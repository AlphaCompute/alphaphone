# Cloud recovery and native qualification follow-up

The current candidate bounds Cloud read-delegation completion to one attempt per callback or explicit status action, followed by one read-only status check. The previous renderer reproduced four completion calls from one action while the server kept reporting `waiting`. Pending secure state remains available after an ambiguous result; `finishing` never triggers another completion. A later explicit status action may attempt completion only after a fresh authoritative `waiting` response. The server's atomic consumed-state check remains authoritative; this is not blind token replay or a promise of idempotent exchange.

After secure pending-state clearing, the renderer rechecks current account/cancellation state before publishing success/failure or invoking `onConnected`. A held-clear rendered test reproduced the old stale callback after account replacement. It did not demonstrate cross-owner credentials or data mutation; the repair removes that stale callback without overstating the finding. Same-owner success, lost response/reload, cancellation, held completion/account change and revocation recovery remain covered.

Primary Cloud sign-in is a separate single-consumption CLI-session flow.
