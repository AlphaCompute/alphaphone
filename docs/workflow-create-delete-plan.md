# Remaining New, Delete and scheduling flows

Read-only audit after Build72 metadata acceptance. No runtime, provider, account, device or source mutations were performed for this plan. References below refer to the isolated reviewed Eliza source lineage recorded under `patches/eliza`, not an edited vendor checkout.

## Next bounded implementation: reviewed Delete with preserved receipts

The current Delete button remains unavailable. Existing backend deletion is not safe to wire directly: `embedded-workflow-service.ts:deleteWorkflow` separately captures a revision, deletes the definition, then removes trigger tasks. There is no expected version or idempotent receipt. A process failure can split those steps. It does not cancel running work. `workflow-service.ts:requireExecutionOwner` resolves ownership from the current definition, so deleting that definition also makes existing execution/approval receipts inaccessible to the owner. Existing worker recovery can still locate the archived source revision; losing UI access does not imply the work stopped.

Implement a reviewed lifecycle mutation, not a call to the existing DELETE route:

1. Show exact workflow name/version and consequences: remove from the active list, prevent future admissions, preserve previous execution receipts. Refuse while any execution is nonterminal; offer the existing explicit per-execution cancellation flow, then require a fresh delete review. Deletion does not imply rollback of past effects.
2. In one owner-scoped transaction, lock the definition, check immutable mutation identity and expected version, recheck all executions terminal, capture the revision and mark a durable tombstone. Preserve owner identity and source revision for historical receipts. Store immutable deletion receipt and pending trigger-cleanup state. A duplicate exact mutation reads that same receipt; stale or conflicting identities cannot delete a replacement version.
3. Complete/recover trigger cleanup idempotently. Admission must already reject tombstoned workflows, so a stale trigger cannot execute during cleanup or after restart. Report pending cleanup separately from completed cleanup; do not turn a lost response into a second deletion request.
4. Repair all relevant mutation/admission boundaries together. `startReviewedWorkflow` already locks the definition, but `startWorkflow` currently reads the definition and then writes its queued execution without a common transaction. `updateWorkflow` and `setActive` also use a previously read snapshot. These paths must lock/recheck the lifecycle state to prevent a concurrent legacy run or stale edit from reviving/starting a deleted workflow. Restore-revision and metadata editing must respect the tombstone too.
5. Lists omit tombstones; execution, approval and mutation receipts use retained owner identity. Phone reconciliation addresses the exact deletion identity even after the item leaves the list. The phone stores only IDs/version locally and clears visible confirmation on account/view change.

Tests: real HTTP/PGlite simultaneous delete/run/edit and owner isolation; refusal with queued/running/waiting-approval work; cancellation then fresh delete; split trigger-cleanup failure plus actual process restart; stale trigger dispatch produces no execution; exact old receipts remain readable to owner but not another owner; dropped deletion response reconciles without another mutation. Native test uses an inactive synthetic fixture, explicit review, response loss, recreation, disappearance from list and retained historical receipt. No Gmail or arbitrary user workflow is used as a test fixture.

Tombstoning here is explicitly receipt-preserving product deletion, not secure erasure. A separate erase-data contract would need to define retained audit/source/engine stores before claiming physical deletion.

## New workflow: a typed reviewed specification, not generated executable source

Current `generateWorkflowDraft` returns model-produced Smithers source, and `deployWorkflow` accepts source and can update an existing ID or activate based on supplied fields. `validateSmithersSource` checks an import/default export and rejects obsolete package names; it is not a permission sandbox. The worker imports the module before evaluating gates, so top-level source can act before an Approval node. Consequently, presenting a friendly generated step list cannot make direct deployment/preview safe.

A complete phone authoring flow should be describe → structured draft → editable supported trigger/steps → exact account/effect review → save inactive → explicit bounded test → exact-version enable. Concrete implementation boundaries:

- Add a versioned, strict typed specification and an advertised operation/trigger catalog. Model generation may propose this data only. Reject unknown operations, fields, accounts and unresolved destinations; do not accept executable source, arbitrary plugin invocation or credentials from the phone/model.
- Compile accepted specifications deterministically into server-owned reviewed templates, or interpret the typed specification in a constrained executor. User draft text is data. A template revision/spec hash is part of the review identity. No user-provided top-level module executes during draft generation, save or preview.
- Start with operations backed by real existing typed contracts. Existing phone `create_note`, `create_reminder`, `open_view` and `browser_navigate` proposals require an explicitly selected registered device and their existing approval/claim/receipt path; they are not a general unattended workflow RPC. Cloud Gmail actions, connector accounts and agent-generated prose must not become implicit device authority. Unsupported palette choices should state the missing capability and remain unselectable.
- Persist inactive creation using owner+creation UUID+exact spec/template revision, with a durable immutable receipt. Reject supplied existing IDs and `active:true`; don't reuse `deployWorkflow` update behavior as idempotent creation. Reconciliation must work after response loss and process restart.
- Preview validates and displays resolved effects/accounts; it executes nothing. A real Test is a separately reviewed run with the existing durable submission identity. Side-effect steps use canonical exact-payload approval and typed execution receipts. Test completion cannot automatically enable a schedule.
- Add exact-version activation admission after successful review; existing GET-then-activate has a race. Keep an explicit unsupported state if a requested account/operation is absent rather than generating an inert workflow and presenting it as complete.

Required tests include malicious/unknown spec rejection before any source import, exact account/device binding, creation key reuse and concurrent creation, response loss/restart, changed template/spec refusal, no effects on draft/preview/save, explicit test versus enable, cancellation during approval, and real native draft editing with unsupported fields absent. Each supported action needs its own actual receipt verification, not just a generated diagram.

## Scheduling remains a separate execution gap

The current backend stores only `{cron,timezone,enabled}`. `syncSchedule` removes then recreates task state outside the definition mutation transaction. `computeNextCronRunAtMs` scans future UTC minutes for civil-time matches; this alone does not define user-visible gap/fold, missed-run or overlap policy. Legacy `startWorkflow` performs find-before-insert idempotency without the new manual-submission transaction, so manual acceptance does not prove duplicate scheduled dispatch is prevented.

Before exposing prototype Once/Daily/Weekdays/time/place/message/email triggers, add advertised typed trigger capabilities and explicit policies. For time triggers, use an immutable occurrence identity and atomic admission, define timezone/DST fold/gap and missed-run handling, make activation/version and trigger reconciliation durable, and define overlap/cancellation behavior. Event/place/mail triggers require their actual consented source and revision/account identity. They cannot reuse prototype trigger objects as executable requests. Validate real scheduler delivery, repeated delivery, restart, revocation, concurrent disable/delete and DST boundaries using synthetic effects first; native notification/reminder tests are not workflow scheduler acceptance.

Cloud workflow management and enclave deployment remain unaccepted. This plan does not change that boundary.
