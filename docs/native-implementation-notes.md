# Alpha Phone native implementation notes — 2026-09-29

The product-owned `DailyApps` Capacitor bridge delegates daily tasks to Android apps and system pickers. It does not introduce an agent runtime, scheduler, provider account, credential vault, or a privileged browser. It remains separate from the pinned upstream plugins and pristine baseline.

## API and actual semantics

`capabilities()` returns `platform: android` and an `actions` array with `action`, `available`, and `mode`. Availability means Android resolves the intent, not that a provider is signed in, a server is reachable, a peripheral works, or a completed operation can be verified.

`perform({action, query?, title?, body?, url?, startTime?, endTime?})` returns `action`, `status`, and optional `message`, `uri`, `name`, `mimeType`, or `transcript`. Status is `opened`, `selected`, `cancelled`, `unavailable`, or `failed`. `opened` means only that an external activity was launched. Never translate it to sent, saved, scheduled, uploaded, or delivered.

| Action | Native ownership | Product responsibility and limit |
| --- | --- | --- |
| camera | Native still-camera activity | Camera controls and saved media stay in camera app; no image capture receipt returns |
| photos | Storage Access Framework image selection | Return only user-selected content URI; product may preview via `Capacitor.convertFileSrc`; no gallery-wide grant |
| files | Storage Access Framework document selection | Return selected content URI/name/MIME; selection is not upload or agent sharing |
| maps | `geo:` view intent | Query is URI encoded; provider, navigation, location and offline map behavior belong to chosen app |
| calendar | Installed calendar activity | No event listing or account synchronization claimed |
| calendar-create, reminder | Calendar event insertion editor | Title/body and epoch-millisecond begin/end; user reviews and saves in calendar; alert delivery is unverified |
| email | `mailto:` draft editor | One validated recipient, subject/body; no direct send; no send completion callback |
| inbox | Installed email activity | No inbox ingestion, OAuth or provider read permission |
| browser | External `http:`/`https:` activity | Reject file/content/javascript/intent URLs and embedded credentials; remote content never receives Capacitor bridge |
| notifications | Current package's Android notification settings | No listener grant, notification ingestion, posting or push registration |
| settings | Android settings | No privileged settings changes |
| autofill | Android settings | User navigates to passwords/autofill to select installed provider; no password read or provider enablement claim |
| voice | Android speech-recognizer activity | User reviews returned transcript; recognizer may use its own network service; no transcription if recognizer absent |
| phone | Dialer | Encoded number prefill; user chooses whether to call |
| messages | SMS editor | Encoded recipient/body prefill; user chooses whether to send |
| contacts | Native contacts activity | No address book read permission or ingestion |

## Result lifecycle and permissions

System document selection accepts `content:` URIs only and retains the read grant if the provider offers persistable permission. Provider failure returns `failed`; cancellation produces no URI. A single selection may be pending. On process restoration, Capacitor restores the pending activity result; the plugin emits retained `restoredResult` for the reloaded renderer to inspect. The renderer must not automatically save/send a restored transcript. A complete process-death acceptance test is still required.

Daily app handoffs introduce no new dangerous permissions; the separate local-reminder flow requests POST_NOTIFICATIONS at point of use. The app does not request camera, microphone, contacts, storage-wide, calendar, phone-call, SMS, notification-listener, or system settings-write grants. The external activity owns its own permission prompts. Installed-app package visibility is scoped to declared actions; there is no `QUERY_ALL_PACKAGES`.

Both install flavors dispatch `alpha-back` to the product renderer. Native launcher HOME intents still dispatch `launcher-home`. Android keyboard dismissal and lifecycle behavior require the actual emulator suite, separately from compilation.

## Upstream findings

`vendor/eliza/plugins` contains native camera, filesystem, location, phone, messages, contacts, system, browser-surface, talkmode, secure-store and other candidates. Their names alone do not establish Android support. At the current pin, `plugin-native-calendar/package.json` describes Apple EventKit and registers only iOS; `plugin-native-reminders/package.json` targets macOS and has no Android source. These cannot satisfy Android calendar/reminder requirements by being imported. Camera and talkmode do have Android implementations, but adopting their embedded controls/permissions/service configuration is a separate source-pinned integration requiring end-to-end evidence.

## Autofill source check

Android's public provider-enablement intents require a provider package and report whether the selected provider belongs to that caller. Alpha Phone is not a credential provider. The bridge therefore does not pass Alpha Phone's package to pretend to enable autofill. A future selected password manager should own its enablement flow and vault unlock UI. The generic settings handoff is intentional until the chosen provider is integrated and verified.

Sources: [Android autofill service guidance](https://developer.android.com/identity/autofill/autofill-services), [Settings API](https://developer.android.com/reference/android/provider/Settings#ACTION_CREDENTIAL_PROVIDER), [Android 15 Settings manifest](https://android.googlesource.com/platform/packages/apps/Settings/+/refs/heads/android15-release/AndroidManifest.xml).

## Real device-local reminders added in this implementation

The calendar editor remains available for account/calendar-backed events, while `scheduleReminder`, `listReminders`, and `cancelReminder` now implement actual device-local notifications. Schedules are private SharedPreferences records, driven by Android `AlarmManager.setAndAllowWhileIdle` with RTC wakeup and immutable, explicit PendingIntents. No exact-alarm access is requested. Delivery is inexact and can be delayed by Android battery policies; the UI must say so. `POST_NOTIFICATIONS` is requested only at scheduling, and `RECEIVE_BOOT_COMPLETED` restores active schedules after normal unlocked boot. Startup/package-update restoration handles process restarts and updated APKs. Force-stop suppresses Android alarms until the user reopens the app; this is an Android platform boundary.

`scheduleReminder({id,title,body?,at})` accepts a 1–100 character ASCII letter/digit/underscore/hyphen ID, title up to 200 characters, details up to 4000 characters, and future epoch-millisecond time. It resolves `{status: scheduled|permission-denied|past|failed,id,mode:inexact,at?,message}`. Notification channel denial is checked as well as runtime permission. A matching ID replaces the old alarm. A successful return means record persisted and OS scheduling call completed, not that a future alert is guaranteed to be seen.

`listReminders()` returns `{reminders,notificationsEnabled}`. Each record includes ID/title/body/at/mode/createdAt and status `scheduled`, `posted`, `cancelled`, or `permission-denied`, with `postedAt` or `cancelledAt` when appropriate. `posted` means `NotificationManager.notify` was called and its timestamp persisted; it does not prove a human saw or heard the alert. Permission revoked before delivery records `permission-denied`. App storage capacity is 250 records, pruning oldest terminal history when necessary while preserving active schedules.

`cancelReminder({id})` persists cancellation before cancelling its alarm/active notification, resolving cancelled/not-found/failed. The receiver checks the stored status under the same process lock, preventing a cancelled alarm callback from posting afterward. Notification text is private on the lock screen, with a generic public version. Tapping a notification emits retained `reminderOpened` with the exact ID so the renderer can navigate to the saved reminder. It does not execute reminder text as an agent command.

The additional instrumentation test schedules a genuine short-delay OS alarm, observes a real active notification and persisted `postedAt`, opens its notification PendingIntent, verifies the exact reminder context event, cancels the active alert, and checks rejection of past scheduling. It grants notification permission to the test package as a fixture. The corrected build44 recovery matrix additionally passed actual notification-permission revocation, retained failed-reminder UI across Activity recreation, explicit same-ID UI retry, and actual emulator reboot delivery for both distribution packages. See [calendar/reminder audit and exact artifact evidence](calendar-reminder-audit.md#corrected-build44-emulator-evidence). The launcher package was installed without assigning/verifying HOME; launcher-role boot is not established. Force-stop behavior, channel denial, Doze delay, clock/timezone changes, OEM scheduling restrictions and physical alert visibility still require separate acceptance evidence.

## Debug-only real-provider development bridge

`DevelopmentAgentPlugin` exists only in `android/app/src/debug/java`; `MainActivity` registers it by reflection inside the compile-time `BuildConfig.DEBUG` branch. Release source sets have no class or development network-security resource. Debug permits cleartext only to `127.0.0.1`; every native development request uses the fixed `http://127.0.0.1:47831` endpoint through a host-provisioned `adb reverse`. Redirects and proxies are disabled. There is no arbitrary URL field.

The host provisions an opaque token into app-private `files/development-agent-token`. Native code reads a bounded token; the token is never returned to the renderer, added to a URL, or logged. `status()` reports configured/connected flags and authenticated service session/model/provider-origin metadata. `chat({requestId,text,context})` sends a bounded authenticated request on a worker, returning text and up to four strictly validated proposals for creating a local note or opening an app view. The native bridge preserves exact context revision and expiry; the renderer requires a separate explicit approval before a local operation. `cancel({requestId})` disconnects the local request and rejects its pending callback. Requests have connection/read deadlines and size limits; the server must independently cancel its provider operation when the response connection closes. Cancellation cannot establish that a provider stopped billing or processing immediately.

This is a real-provider testing path, not production Alpha pairing, account authorization, cloud endpoint rollout, or a tool-execution service. No native development method executes agent proposals. The only enabled actions are bounded local note creation and view navigation, executed by the renderer after explicit approval; mail, payments, credentials, native intents and other external actions are excluded. The app must label this connection as development. The provider secret stays on the host service; it is not copied into Android. Release validation must inspect APK classes/resources and manifest to establish that the development class and loopback cleartext exception are absent. The new instrumentation test verifies missing/invalid private tokens fail closed and Android network policy allows loopback while forbidding cleartext to other hosts; live-provider success is a separate host/service/device flow.

### Reminder lifecycle audit

A rescheduled reminder keeps the same PendingIntent identity, but an old broadcast may already be in flight. The receiver rereads the latest persisted record under the same synchronization lock used by schedule/cancel, refuses to post before its latest timestamp, and re-arms that timestamp. A cancelled record is ignored even if Android already dispatched its former alarm. Notification updates use the stable reminder ID as tag and `onlyAlertOnce` to reduce duplicate alerting.

The receiver is not exported. Android system boot/package-replacement broadcasts and the app's explicit alarm PendingIntent can reach it; arbitrary other applications cannot invoke its custom delivery action. Recovery is after normal user-unlocked boot, not locked boot. Absolute RTC timestamps remain unchanged across timezone changes. Revocation at delivery records permission-denied and does not automatically post old reminders merely because permission is later granted. The original Calendar detail now retains the failed reminder with a clear explanation; Edit → choose a future time → Save explicitly retries it. Restore handles records independently so malformed data does not suppress healthy reminders.

`NotificationManager.notify` and the persisted posted receipt cannot form an Android-wide transaction: process death between those calls can leave a scheduled record and cause restoration to replace/repost the same notification tag. If the original was dismissed before restoration, a repeated alert is possible. Physical hardware/Doze acceptance, launcher HOME-role reboot acceptance, and an explicit unknown-delivery reconciliation policy remain necessary before treating this as a guaranteed reminder service.

## Debug local voice path

A separate debug-only `RECORD_AUDIO` capability now records one foreground microphone draft through Android MediaRecorder. Capture, stop and upload are separate explicit calls: `startRecording`, `stopRecording`, `transcribeRecording({recordingId,requestId})`, `cancelRecording`. The audio is AAC/M4A, mono, 16 kHz/64 kbps, app-private, bounded to 4 MiB. Capture automatically stops at 59 seconds (leaving encoding-frame margin below the host's strict 60-second limit) or when the app leaves the foreground, emitting `recordingStopped`; neither condition automatically uploads it. Successful transcription or explicit discard deletes the clip; abandoned crash files are removed on the next debug-plugin startup.

Only an explicit transcription call sends the chosen private draft over authenticated localhost/ADB transport to the local host's `/transcribe` endpoint. This development route uses the host's local whisper.cpp model; audio is not sent to the chat model provider. The renderer receives text for review, not automatic note saving or agent submission. Cancellation disconnects transport; bounded host processing independently enforces cancellation/deadline limits. Failure retains the draft for explicit retry or discard.

An Android instrumentation test starts the actual microphone recorder, stops it after 1.5 seconds, verifies a nonempty app-private file, discards it, and verifies that a discarded recording ID cannot be uploaded. This demonstrates capture lifecycle; it does not establish speech-recognition accuracy, physical microphone acoustics, or real-person acceptance. Release APKs must continue to exclude RECORD_AUDIO, DevelopmentAgentPlugin/DevelopmentVoiceCapture, and debug localhost network configuration.

## Opt-in global assistant entry

AlphaAssistActivity is an exported ACTION_ASSIST + DEFAULT candidate for Android's user-selected assistant role. Settings can request `ElizaSystem.requestRole({role:'assistant'})`; no role is silently granted. The activity uses a separate application-specific assistant task, excluded from Recents, preserving the invoking app's stack. Root Back and `DailyApps.closeAssistant()` finish that surface even in launcher builds. The latter returns `{closed:boolean}` and cannot close the ordinary launcher. `DailyApps.assistantInvoked` is retained and contains only `{source:'android-assist',surface:'assistant'}`. `DailyApps.appResumed` is retained with `{}` so each renderer can refresh persisted state after another surface modifies it.

All incoming assist extras, data and text are discarded before Capacitor sees the activity intent. There is no VoiceInteractionService, overlay permission, automatic microphone activation, screenshot read, assist-structure parsing, or automatic agent call. Android itself may construct optional assist context before dispatch; the app does not consume it. Each assistant activity has an independent renderer and in-memory connection, while same-origin localStorage is shared; the renderer must refresh/merge persisted state before writes and preserve unsaved local drafts. Candidate/explicit activity instrumentation is distinct from selecting the role and invoking the real system assistant gesture, which requires device acceptance.

Official API basis: https://developer.android.com/reference/androidx/core/role/RoleManagerCompat#ROLE_ASSISTANT and https://source.android.com/docs/core/permissions/android-roles permit an ACTION_ASSIST activity as a role candidate. This deliberately uses the smaller opt-in activity surface instead of importing upstream voice-service behavior.

## Owned video range response correction (September 30, after build40)

Build40's real playback succeeded, but a same-origin `fetch` with `Range: bytes=16-31` failed before receiving headers. The native interceptor reported 206 with no Java exception; this was not evidence of a CORS problem.

Chromium's Android `InputStreamReader::Seek` first computes request-range bounds using the Java stream's `available()` value and then calls `skip(start)` itself. The old implementation had already positioned the file at `start` and bounded the stream to the 16-byte response. Chromium therefore tried to apply start 16 against available length 16, failed the bounds check and returned a generic network error before exposing the native 206 headers. [Chromium InputStreamReader source](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/embedder_support/android/util/input_stream_reader.cc)

The corrected response leaves the file at offset zero and reports the underlying file's remaining availability for Chromium's bounds computation. Chromium performs the single start skip. The wrapper bounds actual reads and skips at requested `end + 1`: this remains necessary because `ReadRawData` directly reads the stream and the loader's `ReadMore`/`DidRead` loop continues until EOF rather than limiting reads by expected content size. The 206 status, exact Content-Range/Content-Length, process-scoped capability and same-origin/MediaStore-ownership checks remain. [Chromium Android stream loader source](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/components/embedder_support/android/util/android_stream_reader_url_loader.cc)

Instrumentation still requires exact response bytes 16–31 to equal the independently read MediaStore bytes. Failure diagnostics now include native request counters before/after and the bounded numeric requested range; they never print the capability URL or media contents. This source correction has not yet passed a rebuilt emulator test. Both standalone and launcher media matrices remain required.

## Calendar civil dates and DST source correction

CalendarProvider marks all-day entries as timezone-independent and requires UTC-midnight boundaries ([Android Events reference](https://developer.android.com/reference/android/provider/CalendarContract.Events)). The product adapter now derives their date offset from UTC date components, retains the exclusive end date, shows them in a compact all-day row using existing calendar tokens, and excludes them from timed timeline geometry. Multi-day all-day entries appear on every covered day; detail shows “All day” and the actual inclusive displayed date range. Complex/all-day editing still hands off to Android Calendar.

Timed event geometry uses the local wall-clock endpoint difference, so a spring transition from 1:30 to 3:30 displays the actual end time. Form save constructs both requested wall-clock endpoints and round-trips every civil component before permission or writes. A nonexistent DST start/end is rejected with the draft retained. Ambiguous fall-back times still use JavaScript's earlier occurrence; explicit timezone/fold selection remains a separate product gap.

`CalendarFlowInstrumentedTest` adds real CalendarProvider fixtures for a two-day all-day event and a DST-crossing timed event. It verifies date membership, no duplicate timed block, all-day detail, nonexistent-time write rejection, corrected-time persistence, and exact timestamps. Tests temporarily use America/Los_Angeles and restore the previous device timezone and automatic-timezone setting in cleanup; only uniquely owned fixture records are removed. Source typecheck passed. Android compilation and both-variant execution are pending the parent build.

For a selected day containing a real timed event before 7am, the product adapter now prepends only the required early hours, shifts events/hour rules/current-time marker using the unchanged 56px hour spacing, and extends the timeline minimum height. Days without early events and reference fixtures retain the 912px timeline. The DST provider test scrolls the actual event into view, verifies it is wholly within the scroll container/viewport and wins center-point hit testing, then injects a real Android touchscreen tap to open detail. This replaces the earlier offscreen DOM-click shortcut; device execution remains pending.

## Repeated-hour and multi-day CalendarProvider intervals

Native timed events now create temporary layout segments for each intersecting local day; intervals use an exclusive end, daily geometry is clipped to 0–24, and all segments retain the original provider identity and `nativeEvent` timestamps. Calendar day/week/month occupancy includes continuation days. The hour axis expands only when actual visible records need midnight/early/late hours; normal prototype spacing and default geometry remain.

Native detail no longer derives an end time from a clamped layout duration. Cross-date events show both dates. Offset-changing intervals show actual clock endpoints with explicit UTC offsets, including equal or backwards repeated-hour endpoints. For a nonpositive repeated-hour wall span, only the visual block height uses elapsed time; displayed event facts remain provider values.

Local editing is refused when the simple form cannot reproduce both exact original timestamps, including cross-date, offset-changing, second-fold or sub-minute events. These edits explicitly hand off to Android Calendar with original event ID/begin/end rather than opening a lossy title-only form. No native provider data is split or rewritten to render the timeline.

Two additional CalendarFlow tests use real provider records under a uniquely named temporary local calendar (with the product account identity to exercise the edit guard). They verify equal/backwards fall-back endpoints, overnight and multi-day continuation membership, bounded daily rectangles, visible Android touches, and unchanged exact provider timestamps. The edit boundary is tested with an Android ActivityMonitor that captures and cancels only the exact fixture event's external VIEW intent; this proves correct handoff arguments and no local rewrite, not operation of an external Calendar app. Existing timezone/settings cleanup remains. Source typecheck passed; build45/emulator results are pending.

## User-selected Files tree (build49 emulator checkpoint)

`AlphaFiles` opens Android `ACTION_OPEN_DOCUMENT_TREE`; it adds no broad storage permission. Android grants the chosen tree, and only an actually retained readable URI grant is restored. Renderer requests use process-scoped IDs issued from that tree's queried documents. Provider flags plus the current persisted write grant control create/rename/delete/move capabilities; unavailable, cancelled, revoked, unsupported, conflict and uncertain-operation results remain distinct. Switching roots releases only this plugin's previously recorded tree grant; Forget releases the current tree and clears its capabilities. [Android SAF guidance](https://developer.android.com/training/data-storage/shared/documents-files)

Production Files reuses folder rows, grid/list geometry, menus and selected-document preview. Choose folder and Saved folder are explicit affordances; create/rename/move use an in-app sheet with existing tokens. File deletion requires a separate permanent-delete confirmation identifying the item and absence of integrated trash/undo. Root deletion, nonempty-folder deletion, directory moves, cross-tree moves, bulk operations and automatic agent mutations are not supported. Supported file moves operate within the selected tree and reselect the resulting provider identity. Preview operations reuse existing bounded text/PDF/image handling; tree preview grants are transient.

The native bridge re-queries metadata and checks an expected revision before rename/move/delete. This detects stale UI metadata but is not an atomic provider transaction: generic SAF providers offer no compare-and-swap mutation. A nonempty-folder check likewise cannot eliminate concurrent external changes between query and provider deletion. Listings show at most250 entries with explicit truncation and a process registry bounded to2048 entries; pagination, cloud-provider offline/timeout qualification and multi-root management remain gaps.

`FilesTreeInstrumentedTest` seeds only `Download/AlphaTree-<UUID>/source-<UUID>.txt`, obtains a real DocumentsUI tree grant, creates/renames a child folder, previews exact file bytes, cancels permanent deletion, moves the file, recreates the Activity and restores the selected root, confirms permanent file/empty-folder deletion, revokes the actual persisted grant and requires a truthful revoked state. It then reauthorizes the same disposable root for narrow cleanup. It refuses to replace an existing selected-tree preference. Test requires English AOSP DocumentsUI and an external-storage provider supporting these operations; unsupported providers must be tested separately without calling those mutations successful. Build49 passes typecheck, repository verification, Android lint and all four APK builds. The complete real DocumentsUI/provider test passes on both standalone and launcher; exact artifacts and logs are in `test-results/prototype-build49/focused/`. Build49 also fixes the destination-loading race by repainting immediately, clearing stale destination state, disabling busy controls, and requiring a loaded writable destination distinct from the source parent. Physical-device, other-provider and separate-process tree restoration remain unverified.
