# Local Camera Scan

Camera Scan captures and retains a photo, runs English OCR on this device, and opens an editable review dialog. Copy uses the clipboard only after a click. Save to Notes writes the corrected text through the existing Notes persistence boundary and reports success only after a confirmed commit. A failed or uncertain save retains the text and disables repeat submission. Scanning does not send pixels or text to the agent or a model provider.

The same renderer implementation and packaged assets are used by browser development and Android web assets. Actual Android WebView execution and physical camera accuracy remain unverified in this browser-only pass. The scan tools additionally support reviewed document boundaries, multipage drafts and searchable PDFs; their later evidence is recorded in the browser review. Event suggestions recognize bounded explicit English dates and times, as detailed below. General natural-language interpretation and automatic language selection remain open requirements.

## Runtime and packaging

`local-ocr.ts` supplies Alpha’s packaged asset configuration to the pinned upstream Files document engine, which owns a classic Worker from creation through termination. It uses the pinned Tesseract.js 7.0.0 worker protocol because the high-level asynchronous createWorker call exposes its handle only after model initialization. The real-engine browser test checks that protocol. Leaving Camera, hiding the page, closing the dialog or pressing Back cancels and terminates the worker, including while loading the model. One recognition is bounded to 60 seconds; input is JPEG/PNG/WebP up to 16 MB and 32 million pixels, resized to a maximum 2048-pixel edge. Review text is limited to 100,000 characters. Recognition accuracy varies with focus, orientation and print quality; users review the result.

`local-ocr-assets.ts` serves an exact allowlist under `/ocr/` in development and emits the same files into `web-dist/ocr/` for packaging. The package lock pins worker 7.0.0, core 6.1.2 and English data 1.0.0. Scalar, SIMD and relaxed-SIMD LSTM cores contain their WASM; feature detection selects one. No CDN defaults are used. The compressed English integer model is approximately 2.95 MB; the three JavaScript/WASM cores total approximately 11.7 MB. Only one core loads per scan. Total packaged assets are approximately 14.8 MB; model caching is disabled in the OCR library.

Upstream API and local installation references: [Tesseract.js API](https://github.com/naptha/tesseract.js/blob/master/docs/api.md), [local installation](https://github.com/naptha/tesseract.js/blob/master/docs/local-installation.md). The worker and core license files ship beside the assets. The [tessdata repository Apache 2.0 license](https://github.com/naptha/tessdata/blob/gh-pages/LICENSE) is retained in `licenses/tessdata-APACHE-2.0.txt` and emitted with the model. The npm language package metadata separately declares MIT; it wraps the upstream trained data.

## Browser evidence

`test/browser/local-ocr.spec.ts` uses real Tesseract worker/WASM/model execution. It verifies recognizable generated print, local asset requests with no remote requests, early cancellation, Camera Scan through a synthetic camera stream with real JPEG/IndexedDB and Notes reload, retained text on an explicitly injected unconfirmed save, and cancellation while model loading is held. Synthetic camera pixels and injected persistence failures are test fixtures, not hardware evidence. Existing browser camera save/denial/late-permission cases are also rerun. No Android build is performed.

## Photo PDF export

The scan review now shows the captured image and offers **Download photo PDF** in a browser or **Save photo PDF** on Android. The generated document contains one image page, fitted without distortion inside A4 portrait or landscape margins. It includes the photo rather than corrected OCR text; the UI states this distinction. Reviewed corrections still use Save to Notes. Input is decoded locally, resized to a 2048-pixel longest edge, converted to JPEG and embedded with pinned `pdf-lib` 1.17.1, loaded on demand. Its MIT license ships with the local scan assets. See the [PDF-LIB image embedding API](https://pdf-lib.js.org/docs/api/classes/pdfdocument#embedjpg).

Browser export requests a real `.pdf` download and does not claim a confirmed filesystem save or automatic insertion into Browser files. Android calls the existing AlphaNoteDocuments plugin with a bounded PDF payload and an explicit `ACTION_CREATE_DOCUMENT` picker. It writes only the user-selected URI, reads the bytes back, and reports confirmed success only on exact equality. Provider write/readback failures remain unverified outcomes; the review prevents repeat export, except after an explicit picker cancellation. Closing or hiding the scan cancels PDF preparation before the document API is called. A picker/write already dispatched may still finish; closing the review does not reverse it.

Browser tests inspect the downloaded PDF structure and portrait/landscape geometry, verify a real image resource, cancellation and invalid input handling, and keep all action buttons inside the dialog at 360×740 dark and 1440×500 light. A Poppler-rendered landscape export was visually inspected, and text extraction was empty as expected for an image-only PDF. A host-Java harness exercises the same native payload/readback helper against malformed and oversized encoding, truncation, added bytes, changed bytes and non-progressing reads. This is not Android picker or device acceptance; no APK build was run. This was the initial photo-PDF checkpoint. Later document correction, multipage drafts and searchable-text reviews are implemented; consult the current browser review for their bounded evidence. General event interpretation and additional languages remain open.

## Reviewed website links

Recognized or corrected text now supplies an expandable **Review links** list. Each entry shows its full normalized HTTP/HTTPS address before an explicit Open link action. Browser development uses a new tab with no opener or referrer; Android uses the existing browsable system-intent handoff. No address is fetched, prefetched, sent to the agent or opened merely because OCR detected it. Corrections immediately update the list, and retired or removed links cannot navigate through their old controls.

Detection handles explicit HTTP/HTTPS and `www.` tokens, quoted addresses, surrounding punctuation, duplicate URLs and international hostnames displayed in ASCII/punycode. It does not guess bare domains, join OCR lines or convert active schemes to search. Credentials, backslashes, malformed authority syntax and oversized candidates are excluded. At most ten unique destinations are shown; users can correct the source text. A recognized URL can still be misread, so the review asks users to compare the full address with the photo.

Tests use real OCR on a generated URL image and intercept the eventual destination with a local test response. They verify no pre-click request, correction replacing the destination, stale/retired controls failing closed, and a new page with `window.opener === null`. This qualifies the browser review and navigation path. Android intent dispatch is existing code; no new Android/device acceptance is claimed. This link-only checkpoint did not qualify the later document-boundary, multipage and searchable-PDF tools; their current evidence is in the browser review.

The URL test also exposed a real OCR character error in the generated sample hostname. The test now checks that the displayed destination matches the actual OCR result, then verifies explicit correction before opening. Link detection is not a guarantee of transcription accuracy.

Qualification for this link change: 77 repository tests, typecheck and production web build passed on the fixed candidate; 12 combined OCR/PDF/link browser cases passed. The two link cases were rerun after adjusting screenshot scroll position. No Android build was run.

## Reviewed event drafts

Camera Scan offers **Create event draft** after OCR completes. The first nonempty line supplies an editable title. A single valid explicit date can use `YYYY-MM-DD`, `October 10, 2026`, `10 October 2026`, or three-letter English month abbreviations with optional periods and ordinal day suffixes. A year is required; invalid dates, conflicting dates, omitted years alongside other recognized dates, and ambiguous numeric day/month formats leave the date blank.

Standalone `18:30`, `6:30 PM`, `7 p.m.`, and `12 AM/PM` lines can suggest a start time. `Time:`, `Start:`/`Starts:`, `at`, and an ISO date prefix are supported. Conflicting or invalid clock candidates, ranges, recognized timezone abbreviations, IANA-region zone names and explicit timezone labels are left for manual review; a website path such as `example.com/events` is not mistaken for a timezone. A single `Location:` or `Venue:` line may suggest the location; conflicting locations remain blank. No model request, network lookup, inferred year or timezone conversion is involved.

The form shows the device time zone and explicitly states that duration starts at 60 minutes. Title, date, start, duration and location remain editable. Notes preserve the corrected scan text, with Android’s 16,000-character limit enforced before handoff. This is bounded extraction of explicit printed fields, not general natural-language scheduling.

**Review in Calendar** opens the existing Calendar composer with a local-calendar draft. It does not request access, write an event, invite anyone or start a reminder. The user reviews the destination/details and presses the existing **Save event** control. That existing path owns permission checks, conflict handling and verified persistence. Closing the scan retires its draft controls. Invalid dates and nonexistent local start times are rejected before handoff; Calendar retains its own start/end-time validation at Save.

The browser journey uses a synthetic camera stream with actual capture/OCR, corrects the text, checks suggested details, edits title/location/duration, verifies the calendar contains no event before Save, and verifies one persisted event after Save and reload. A component fixture in a modal verifies a New York spring-forward time is rejected and can be corrected. Host tests cover suggestions, absent/ambiguous times, month/year offsets, invalid dates/durations and notes limits. Relative-date interpretation, prose/range extraction, timezone conversion, recurring/all-day event extraction and invitations remain outside this implemented draft path. No Android build or physical-device claim is made.

The existing Calendar composer now displays the full selected date above its horizontal day strip and uses a multiline Notes field. This prevents a future date from being hidden off-screen and preserves legible scanned lines during final review. Qualification: 80 repository tests plus typecheck/build, 14 combined Scan browser cases and light/dark Calendar reference-state checks passed on the fixed candidate.


The October 4 event follow-up renders the English date, AM/PM time and venue in actual synthetic camera pixels, verifies their real Tesseract transcription, then corrects/reviews the text before opening Calendar. The review makes zero writes; explicit Calendar Save produces one event with the exact reviewed source and duration, retained after reload. Unit coverage includes invalid/leap dates, missing years, midnight/noon conversion, conflicting candidates, timezone labels and ordinary website paths.

Firefox can omit classic-worker `importScripts` URLs from Playwright page request events even when recognition succeeds. The local-asset test therefore observes actual imports inside its test worker as well as page requests, preserves real worker/WASM recognition, and still requires the packaged worker, language data and LSTM core with no remote origins. Production OCR code and request policy are unchanged.
