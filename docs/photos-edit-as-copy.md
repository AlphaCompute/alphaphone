The native editor validates the owned, published, nontrashed row and mutation revision, reads at most32MB of encoded source, and decodes one software sRGB snapshot. Both preview and PNG export derive from that same snapshot. Source SHA-256 and current provider revision are rechecked before preview/publication, including Android29 where the provider has no generation counter. Quarter-turn rotation is followed by optional centered crop to `floor(width/1.3)` × `floor(height/1.3)`, matching the reference crop's centered1.3× intent. The preview shows the resulting pixels with contain sizing; it does not pretend a CSS-only transformation modified the source. EXIF location metadata is not copied.

Decoded copies are bounded to2048px on the longest edge. The editor explicitly states when this reduces the source resolution. Native preview is bounded to1024px. Originals are never opened for writing. Cancel/Back, view departure, backgrounding and teardown retire the session; a pending export checks cancellation before publishing. A save already published before departure remains a saved copy.

Save reserves a unique operation identity in private preferences, writes an owned MediaStore `IS_PENDING` PNG, rechecks source/cancellation, and publishes. The unique owned display name allows reconciliation after publication but before receipt persistence. The renderer retains an unresolved operation ID locally and checks its outcome before permitting another save; it never automatically repeats the write. Failed pending rows are removed through their exact owned URI before failure is reported. A bounded128-entry outcome journal reclaims terminal records only; unresolved records are not silently removed. No image is uploaded or placed in agent context. The resulting copy has its own MediaStore ID/revision.

## Reference filter contract and Build73 implementation

The seven existing reference filter controls retain their positions. Build72 left non-Original filters explicitly unavailable. Build73 implements every listed operation with sequential native encoded-sRGB transforms and per-primitive clipping; native equivalence is pending the chart fixture. Source of truth is `PH_FILTERS` in `apps/app/src/prototype/model.js`:

| Filter | Exact reference CSS | Native follow-up |
| --- | --- | --- |
| Original | `none` | Implemented unchanged color snapshot |
| Vivid | `saturate(1.55) contrast(1.08)` | sRGB saturation matrix then contrast1.08 with midpoint offset |
| Warm | `sepia(.3) saturate(1.35) hue-rotate(-8deg)` | Interpolated sepia matrix, saturation, then CSS hue-rotation matrix |
| Cool | `saturate(1.1) hue-rotate(14deg) brightness(1.03)` | Saturation, hue rotation, then channel brightness scaling |
| Mono | `grayscale(1) contrast(1.05)` | CSS luminance weights followed by contrast |
| Fade | `contrast(.78) brightness(1.12) saturate(.75)` | Contrast, brightness, saturation in that order |
| Noir | `grayscale(1) contrast(1.55) brightness(.88)` | Grayscale, contrast, brightness in that order |

Use native ColorMatrix/Canvas or a bounded per-pixel sRGB transform, but verify CSS filter operation ordering, channel clipping between primitives, alpha handling and color-space behavior against a rendered browser color chart before claiming equivalence. A single concatenated matrix can differ when intermediate clamping matters. Apply the verified operation to both preview and export from the same snapshot, include the filter identifier in immutable save parameters, and extend the native asymmetric/chart fixture to assert pixels and original preservation. No image-generation or third-party filter library is required.

Platform contracts: [Android ImageDecoder](https://developer.android.com/reference/android/graphics/ImageDecoder) supplies bounded software decoding; [MediaStore shared-media guidance](https://developer.android.com/training/data-storage/shared/media) documents pending-row publication. TypeScript and whitespace checks pass; root owns Android compilation, both distributions and native validation. Large/oriented JPEG, wide-color/transparency, external-provider imports, process interruption during export and physical-device memory qualification remain separate from this first fixture.

## Measured browser filter reference (APK source frozen during Build72)

`scripts/test-photo-filter-reference.mjs` renders actual CSS-filtered color blocks in headless Chromium151.0.7922.34, reads their screenshot pixels and independently evaluates sequential normalized sRGB formulas. Its65 inputs cover45 opaque RGB cube samples plus20 zero/partial-alpha samples. All seven filters matched **every opaque RGB byte exactly** using floating-point intermediates, per-primitive `[0,1]` clipping, and final byte rounding. Alpha was retained exactly; nonzero partial-alpha RGB differed by at most3 byte levels, including up to2 levels for Original, consistent with premultiplied-alpha quantization. Fully transparent RGB is not meaningful and is not an equivalence assertion.

Artifacts: `test-results/photo-filter-reference/css-chart.png`, `expected-pixels.json` (all455 browser/candidate samples), and `summary.json`. Reproduce with `ALPHA_BROWSER_MODULES=PATH_TO_NODE_MODULES node scripts/test-photo-filter-reference.mjs`. It uses a self-contained chart and does not run the app or contact a provider. Browser version is recorded so future rendering changes are visible.

The candidate uses normalized encoded sRGB channels (no conversion to linear light), saturation weights `.213/.715/.072`, grayscale weights `.2126/.7152/.0722`, the specified sepia interpolation matrix and CSS hue-rotation matrix. Contrast uses `(channel-.5)*amount+.5`; brightness multiplies the channel. Operations execute in the exact reference string order and clip after **each** operation; no byte rounding is introduced between operations. This follows the [W3C Filter Effects filter-function contract](https://www.w3.org/TR/filter-effects-1/#FilterProperty), including its sRGB rule and matrix definitions.

A single combined matrix without intermediate clipping is measurably wrong on this chart: Warm differs by up to14 RGB byte levels, Cool21, and Noir31. Native implementation should use sequential float/double per-pixel operations with clamping rather than concatenate every matrix into one Canvas draw. Keep alpha unchanged; qualify Android premultiplication through native PNG decode/export fixtures against the recorded browser pixels. The chart establishes a precise candidate and golden opaque samples, **not Android filter acceptance**. Implement both preview and export from the same transformed snapshot, bind filter ID into the reserved save operation, and test every reference control, cancellation, original bytes and stale source rejection.

## Build74 shared-PNG and alpha quantization correction

The Build73 filter chart failure remains recorded in `test-results/prototype-build73/photos-edit-filter`: Warm preview sample52 green expected16, observed20 on both distributions. The old Android fixture first generated its source through a premultiplied Bitmap and PNG encoder, whereas the browser chart began with CSS colors. The two paths therefore did not guarantee identical encoded input. A fixed three-level bound on unpremultiplied RGB also does not express the visible contribution of a low-alpha pixel: at alpha64, one stored premultiplied level spans roughly four straight RGB levels.

Build74 uses one canonical650×10 RGBA PNG for both actual Chromium CSS filtering and Android ImageDecoder. Its SHA-256 is `15018eb24bfc1376aa03021edd3f77a881958cb7c4095a58f7b7ebce27c909b8`. `scripts/test-photo-filter-png-reference.mjs` produces it and the independently measured browser screenshot; the checked-in `photo-filter-source.png` and golden JSON bind the same SHA-256. The native fixture asserts this hash before importing those exact bytes into MediaStore. It no longer reconstructs source colors through an Android Bitmap.

Chromium151.0.7922.34 and the independent candidate retain exact opaque RGB and exact alpha across all seven filters. After modeling one premultiplied input/output storage quantization, the largest straight RGB discrepancies per filter are Original0, Vivid0, Warm1, Cool2, Mono4, Fade2, Noir0; their stored premultiplied contribution differs by at most one byte level. This browser measurement passes locally. It is qualified color equivalence, **not translucent straight-RGB pixel identity and not an observed Android pass**. Artifacts are under `test-results/photo-filter-png-reference/`.

The production transform now quantizes the final floating-point result once in the premultiplied storage domain and converts that representable value for Android `setPixels`; it avoids first rounding straight RGB and then quantizing it again. Opaque output keeps its prior exact contract. The native fixture requires exact alpha, exact opaque RGB, and at most one stored premultiplied level for partial alpha. It also performs real Canvas composition of each decoded preview/export over opaque black and white and compares visible channels to the browser golden contribution with that one-level bound (opaque remains exact). Fully transparent RGB carries no visible color, but alpha and compositing are still checked. Every pixel of native preview and export must match exactly; original encoded bytes, immutable filter reservation and duplicate-save identity remain asserted.

`node --check`, TypeScript checking and whitespace checks pass for this checkpoint. Root must compile and run both native distributions before reporting Build74 filter acceptance. This65-color synthetic chart does not prove arbitrary wide-color, HDR, image-size, physical-device or browser-version equivalence.
