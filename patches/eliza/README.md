## Ownership and authorization

The existing `approval_requests` table and `PgApprovalQueue` own every proposal,
decision, execution attempt, and receipt. The new `client_devices` table contains
only enrollment (agent, authenticated subject, installation, enrollment UUID,
SHA-256 key hash, label, and revocation state). It is registered with the existing
SQL schema migrator. It is not another task or approval queue.

Enrollment and every subsequent device request require the normal authenticated
session plus these headers:

- `X-Eliza-Device-Id`: an installation UUID generated by the native client.
- `X-Eliza-Device-Key`: 32 cryptographically random bytes encoded as 64 lowercase
  hex characters, retained only in the native encrypted credential store.
  Bind the storage slot to the verified server origin, agent, authenticated
  subject, and installation; never reuse or forward it across accounts/origins.

The subject comes exclusively from the host's authenticated identity. A verified
scoped host principal is supported under a `gateway:` namespace. A static bearer
or trusted-loopback OWNER bypass without a subject is insufficient. Device
requests explicitly disable that loopback bypass so an actual machine session
is checked even during local development. Request-body identities are ignored.

The model cannot select a subject, device, or enrollment. The authenticated
conversation request supplies the device headers and validates enrollment before
binding an AsyncLocalStorage turn context. That context expires at turn exit.
`PROPOSE_DEVICE_ACTION` can only propose against that active bound context and
revalidates the enrollment for each proposal. It cannot approve or execute.
Plain chat without a bound device keeps working, with this action unavailable.

## HTTP contract

All paths below start with `/api/client-devices`. POST bodies are JSON.

| Method and path | Body | Result |
| --- | --- | --- |
| POST `/register` | `{label}` | `{installationId,enrollmentId}` |
| GET `/proposals` | None | `{proposals:[...ApprovalRequest,digest]}` |
| POST `/proposals/:id/decision` | `{digest,decision:"approve"\|"reject"}` | `{proposal,digest}` |
| POST `/proposals/:id/claim` | `{digest}` | `{proposal,digest}` with execution attempt |
| POST `/proposals/:id/receipt` | `{digest,attemptId,receipt:{outcome:"applied"\|"failed"\|"unknown",operationId?,code?}}` | `{proposal,digest}` |
| POST `/proposals/:id/reconciliation` | `{digest,attemptId,resolution:{confirmed:true,outcome:"applied"\|"not_applied",operationId?}}` | `{proposal,digest}` |
| POST `/revoke` | `{}` | `{revoked:true}` |

An enrollment retry with the exact same key returns the same enrollment. A key
substitution or reuse of a revoked installation is rejected. After revocation,
a new installation ID and fresh key are required.

The full proposal uses the upstream `ApprovalRequest` shape. Important fields are
`id`, `state`, `subjectUserId`, `expiresAt`, `payload`, and `execution`. Its payload is:

```ts
{
  action: "device_action",
  version: 1,
  installationId: string,
  enrollmentId: string,
  operation:
    | {type: "create_note", title: string, body: string}
    | {type: "create_reminder", title: string, dueAt: string}
    | {type: "open_view", view: string}
    | {type: "browser_navigate", url: string}
}
```

`dueAt` is an absolute, valid UTC ISO date/time. `url` must be HTTPS without
embedded user information. The closed view enum is `home`, `notes`, `reminders`,
`browser`, `calendar`, `files`, `photos`, `camera`, `maps`, `inbox`, and `settings`.
Extra operation fields and unknown operations are rejected. Titles are limited
to 256 characters, note bodies to 32,000, and URLs to 4,096; overflow is rejected,
never truncated. Applied receipts require an opaque native `operationId` matching
`[A-Za-z0-9][A-Za-z0-9_-]*`, at most 128 characters. Receipts contain no note body,
email content, URLs with credentials, or arbitrary plugin responses.

The digest binds proposal ID, subject, complete typed payload, and expiry. Treat
it as an opaque server review token and return it unchanged. Proposals expire
after ten minutes. Proposal idempotency includes subject, device, and model
operation key; the same key with changed content is rejected.

Missing session/device headers return 401. Invalid enrollment, stale digest,
expired review, conflicting receipt, and invalid state transitions return 409.
Unknown paths return 404. Runtime/store unavailability returns 503. Conversation
binding rejects unavailable enrollment with 403 and storage failure with 503.
The legacy `/api/approvals` aggregate deliberately excludes these device payloads
because it has no enrollment authority.

## Client execution requirements

1. Render the exact operation, target, and values. A model proposal is not consent.
2. Send the decision only after explicit owner approval or rejection. Bind the
   dialog and native journal to the current account, connection, enrollment, and
   local context snapshot; the server does not trust phone observation metadata
   as authorization or persist its view revision in the proposal.
3. Before claiming, persist the local journal reservation. Revalidate the account,
   expiry, full payload, and local context immediately before a native effect.
4. Claim once. The server locks the enrollment row and atomically advances the
   existing approval to executing and marks dispatch started **before** returning
   the permit. A duplicate claim is rejected, including after server restart.
5. Execute only the four typed operations through allowlisted native handlers.
   The native journal must prevent replay across process death and duplicate UI
   events. A successful HTTP claim is not evidence that the native effect ran.
6. Post the actual native receipt with the exact attempt ID. Identical receipts
   are idempotent; changed outcomes cannot silently overwrite an existing result.
7. A lost claim response or ambiguous native outcome remains uncertain. Do not
   repeat the effect to obtain a successful reply. Consult the native journal and
   request explicit owner reconciliation. An applied reconciliation records the
   existing operation ID. A not-applied reconciliation never dispatches: the old
   proposal remains unclaimable and a fresh proposal/review is required.

Revocation serializes with proposal/claim operations through the same enrollment
row lock. It prevents later admission; it cannot retroactively undo an already
claimed external effect. Account changes must also cancel local presentation and
execution. The server keeps expired/terminal records for journal reconciliation;
clients should not show terminal history as new approvals.

## Validation and remaining integration

The package E2E test uses real HTTP, real AuthStore machine sessions, real SQL
schema migrations, and disk-backed PGlite. It covers two enrolled identities,
key substitution, exact-key reuse, cross-owner isolation, no claim before review,
digest mismatch, durable restarts, concurrent claim dedupe, typed operations,
rejection, receipt dedupe/conflicts, uncertain dispatch recovery, explicit
reconciliation, revocation, and exclusion from the legacy aggregate.

These are server protocol tests. They do not establish model action selection,
Android native effects, remote deployment, or device acceptance. AlphaPhone's
client approval UI, encrypted enrollment storage, durable native journal, and
native handlers must be wired and tested separately. Eliza Cloud shared runtime
has no equivalent durable approval owner at its REST adapter seam; this patch
does not invent a second queue. A Cloud proxy must propagate a verified per-user
principal before device admission; a generic gateway credential is denied.

### Live provider qualification

The proposal tool uses disjoint `anyOf` branches without provider-unsupported `maxLength` annotations; the durable service still rejects extra keys and over-limit values. The previous `type: object` plus `oneOf` wrapper was closed as an empty object by strict normalization, and Cerebras also rejected `maxLength`. A real `qwen-3.8-27b` request now returns HTTP 200 with the typed proposal call. The real app host then passed model proposal, enrollment, explicit approval, claim, desktop fixture journal effect, durable receipt and no-replay resynchronization. Evidence is in `test-results/remote-device-actions`; this does not establish Android or deployed enclave acceptance.

For a source dev host, use consistent `--conditions=eliza-source --tsconfig-override <eliza>/tsconfig.json` resolution. The isolated local profile and machine sessions must remain outside this repository.

### Authenticated current-turn capability grounding

The planner receives a trusted capability instruction only while the host-bound authenticated phone turn is active. Its progressive initial tool surface retains the already-authorized proposal action; role, disclosure, connector and action validation still apply. This prevents stale unavailable-tool replies and invented page-delegation routes from masking a registered phone capability. Eight real ordinary requests (two fresh conversations per supported operation) each returned one pending proposal. Tests rejected every proposal without native effects; an unbound control invoked no proposal tool. See `real-routing-matrix.json` in the evidence directory.

## Egress secret and PII swap

`egress-swap-control-objects.patch` is an Android runtime extra (`android-local-runtime-source.json`) applied after the MVP series. It fixes two upstream defects that kept the secret and PII swaps from protecting hosted model requests:

- Both swap walkers normalized every non-plain object, including the request `AbortSignal`, into a plain record. With either swap on, fetch rejected every model call (`signal is not of type AbortSignal`). The walkers now pass the live `AbortSignal` through.
- `isSecretSwapEnabled`/`isPiiSwapEnabled` read only runtime settings, and host env forwarding rejects any key containing `SECRET`, so a host could never enable the secret swap. Both now fall back to the upstream `ELIZA_SECRET_SWAP_ENABLED` / `ELIZA_PII_SWAP_ENABLED` process environment; an explicit runtime setting still wins.

`AlphaLocalAgentPlugin` sets both switches for the resident agent. `packages/core/src/__tests__/swap-control-objects.test.ts` adds seven cases; without the source change the four defect cases fail. Evidence and coverage limits are in [redaction integration](../../docs/market-research/13-redaction-integration.md): the regex layer replaces email, phone, card, SSN, IBAN, known secrets and street addresses; person names need a registered NER recognizer. The desktop `backend/` builds from the unpatched vendor pin and forwards each switch only when it is `true`; enabling either there fails closed until the vendor pin includes this fix.
